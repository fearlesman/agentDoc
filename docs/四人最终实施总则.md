# 四人最终实施总则

## 常用缩写

- **PSAC**：软件合格审定计划；**SRS**：软件需求规格/标准。
- **IR**：中间表示，即 `ParsedDocument`；**API**：应用程序编程接口。
- **RBAC**：基于角色的访问控制；**OCR**：光学字符识别。
- **MIME**：文件媒体类型；**SHA-256**：文件完整性哈希值。
- **AI**：人工智能生成的机器结论；**CI**：持续集成；**P95**：第95百分位耗时。
- **DOCX/PDF/XLSX**：Word/PDF/Excel 文件格式；**fixture**：固定测试样例；**anchor**：原文定位锚点。

完整术语表以《最终统一数据契约v1.1.md》为准。

## 先读顺序

1. `最终统一数据契约v1.1.md`：唯一可执行字段和接口来源；
2. 本文件：协作边界、验收和共同规则；
3. 你自己的成员任务书：个人实现范围。

旧版协作文档中的 JSON 不得直接实现。

## 统一开发环境约束

团队统一采用：**Windows 11 + Python 3.11 + uv + FastAPI/Pydantic + Node.js 20 LTS + React/TypeScript/Vite + pnpm + Git**。文档解析和报告转换统一使用 **LibreOffice**；项目必须支持在受控内网环境运行，禁止把保密材料上传到外部 API。

仓库必须提交 `pyproject.toml`、`uv.lock`、`package.json`、`pnpm-lock.yaml` 和 `.env.example`；`.venv/`、真实课题材料、上传文件和导出文件不得提交 Git。团队统一通过 `uv sync` 安装 Python 依赖，通过 `pnpm install --frozen-lockfile` 安装前端依赖。数据库和任务队列、UI 组件、OCR 实现等未写入跨模块契约的内部选型，由对应负责人自行决定，但不得破坏 v1.1 接口、fixture 和内网验收。

## 目标闭环

上传 Word/PDF → 解析 → 文档类型识别 → 匹配专用+通用检查单 → 用户确认 → 异步逐条审查 → 证据/位置/风险/建议 → 专家复核 → Word/PDF/JSON 报告 → 历史检索/审计。

样例是 PSAC、SRS 两个 DOCX 和 XLSX 检查单；检查单共 32 条，但单次审查数量由确认后的 `selected_item_ids` 决定，不能写死 32。

## 四人边界

- A：DOCX/PDF → ParsedDocument；只提取事实和位置。
- B：XLSX → Checklist；消费 IR，输出 ChecklistMatch、Review、Finding；不读原文件。
- C：唯一状态/存储/API 入口；负责 Job、RBAC、审计、留存和接口。
- D：只消费 C 的 API；负责 Web、复核提交、报告请求和展示。

## 共同硬规则

- 所有跨模块对象遵守 v1.1；字段变更先改契约和 fixture。
- Document、Job、Review、Export 状态不可混用；非法转换必须报错。
- Finding 不得凭空生成证据；anchor 必须回指 IR；AI 原判不可覆盖。
- `failed` 是审查结论，`error` 是程序执行错误，`needs_review` 是人工确认需求。
- 评测必须包含 PSAC、SRS、通用项，以及解析失败、规则缺失、低置信度、导出失败、越权、过期下载和重复请求。
- 全部公开 API 使用 Google docstring；TypeScript 使用 JSDoc。

## 验收门槛

- ≤50 页端到端耗时 <10 min；
- 每条意见有位置、问题、风险、建议；
- 报告显示 AI 原判与有效最终结论；
- 现场演示正常和异常两场景；
- 评测保存数据集版本、文档 hash、金标准、分母/分子、命令和原始结果；
- 审计覆盖上传、解析、确认、审查、复核、导出、下载和删除。

## 周期

第 1 周：各模块 fixture 和最小实现；第 2 周：解析/匹配/确认链路；第 3 周：审查/复核/导出；第 4 周：两条真实样例链路、异常场景、指标脚本、部署和现场演示。
